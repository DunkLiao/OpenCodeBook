# AI Coding 變更檢查與 PRD 回歸驗證提示詞

請重新檢查**本次所有修改**，確認實作是否符合最新需求，並驗證這些修改沒有破壞 `docs/PRD.md` 中既有的功能、流程與驗收條件。

目前任務是 **Review / Verification**，不是進一步開發。

除非發現明確問題且我另外要求你修正，否則：

- **不要修改任何檔案**
- **不要重構程式碼**
- **不要順手最佳化**
- **不要新增功能**
- **不要改變既有行為**

---

## 一、先確認本次修改範圍

請先檢查目前 Git 工作區與最近的變更，辨識這次實際修改了哪些內容。

可參考：

- `git status`
- `git diff`
- `git diff --stat`
- 必要時查看最近 commit 或 staged diff

請整理：

1. 修改了哪些檔案
2. 每個檔案修改了什麼
3. 這些修改對應到哪一項新需求
4. 哪些修改可能影響既有功能

請只分析**本次變更**，不要把專案中原本就存在的問題誤判為這次修改造成。

---

## 二、重新確認最新需求

請根據目前對話、任務描述、規格文件或專案內相關文件，整理這次要完成的新需求。

請將新需求拆成可驗證項目，例如：

| ID | 新需求 | 實作位置 | 驗證方式 | 結果 |
|---|---|---|---|---|
| N-01 | ... | `src/...` | ... | PASS / FAIL / UNKNOWN |

請確認：

- 每項新需求都有對應實作
- 沒有遺漏必要情境
- 沒有額外改變未要求的功能
- 邊界條件與錯誤情境是否有處理
- UI / API / Data Model / Business Logic 是否一致

如果某項需求無法從現有資訊確認，請標示：

**UNKNOWN — 需要人工確認**

不要自行猜測。

---

## 三、完整閱讀 docs/PRD.md

請完整閱讀：

`docs/PRD.md`

不要只搜尋關鍵字或閱讀局部段落。

整理其中與本次修改可能相關的：

- 核心功能
- 使用流程
- Business Rules
- UI / UX 行為
- API 行為
- Data Rules
- 權限規則
- 錯誤處理
- 邊界條件
- 非功能需求
- 驗收條件（Acceptance Criteria）
- 明確禁止改變的既有行為

---

## 四、建立 PRD 驗收條件對照表

請將 `docs/PRD.md` 中與本次修改相關的需求與驗收條件逐條檢查。

建議格式：

| PRD ID / 章節 | 原有需求或驗收條件 | 是否受本次修改影響 | 驗證依據 | 結果 |
|---|---|---|---|---|
| ... | ... | 是 / 否 | 程式碼 / 測試 / 手動檢查 | PASS / FAIL / UNKNOWN |

結果定義：

- **PASS**：有足夠證據確認仍符合 PRD
- **FAIL**：確認已違反或破壞 PRD
- **UNKNOWN**：目前資訊不足，無法可靠判定
- **N/A**：與本次修改無關

不要因為「程式可以編譯」就直接判定 PRD 驗收通過。

---

## 五、執行回歸檢查

請確認本次修改是否影響原有功能。

優先檢查：

### 1. 核心流程

- 原有主要使用流程是否仍可正常完成
- 是否出現行為改變
- 是否出現流程中斷
- 是否改變預設值或原有邏輯

### 2. UI / UX

若有前端：

- 原有頁面是否仍正常顯示
- 原有按鈕、表單、選單是否正常
- Loading / Empty / Error State 是否正常
- Responsive 行為是否被破壞
- 新功能是否影響既有操作流程

### 3. API

若有 API：

- 原有 Endpoint 是否仍正常
- Request / Response Schema 是否改變
- Status Code 是否改變
- Error Response 是否改變
- 是否造成 backward incompatibility

### 4. Data / Storage

若涉及資料：

- Schema 是否改變
- 是否破壞舊資料相容性
- Migration 是否安全
- Default Value 是否改變
- 資料讀寫流程是否仍一致

### 5. Authentication / Authorization

若涉及權限：

- 原有角色權限是否維持
- 是否新增未預期的存取權
- 是否阻擋原本合法的操作

### 6. Error Handling

確認：

- 原有錯誤處理仍然存在
- 沒有吞掉例外
- 沒有將正常錯誤變成 crash
- 錯誤訊息或狀態碼沒有意外改變

---

## 六、執行現有驗證工具

請先查看專案現有的：

- `package.json`
- `pyproject.toml`
- `Cargo.toml`
- `Makefile`
- CI 設定
- README
- AGENTS.md
- CLAUDE.md
- 測試相關設定

確認專案既有的驗證方式。

如果安全且不會修改專案狀態，請執行適用的：

- Unit Test
- Integration Test
- E2E Test
- Type Check
- Lint
- Build
- Static Analysis

請**優先使用專案既有指令**，不要自行發明新的驗證流程。

如果某個測試或指令無法執行，請說明原因，不要因此假設通過。

---

## 七、特別檢查隱性回歸

除了明顯功能，也請檢查以下容易被忽略的問題：

- 修改 shared component 導致其他頁面受影響
- 修改 common utility 導致其他功能行為改變
- 修改 type / interface 導致相依模組異常
- 修改 API schema 造成前後端不一致
- 修改預設值造成舊流程不同
- 修改 validation 造成舊資料無法使用
- 修改 state management 造成其他畫面異常
- 修改 CSS / global style 影響其他 UI
- 修改 environment variable 或 config 行為
- 修改 dependency 導致版本相容性問題
- 移除看似未使用但實際被動態載入的程式
- 新需求實作覆蓋或繞過原有 Business Rule

---

## 八、不要把既有問題算成本次回歸

如果檢查時發現問題，請區分：

### A. 本次修改造成

有證據顯示問題是由這次變更引入。

### B. 專案原本就存在

問題在本次修改前已存在，與這次修改無關。

### C. 無法判定

目前沒有足夠證據確認來源。

請避免將舊問題錯誤歸咎於這次修改。

---

## 九、輸出最終驗證報告

完成後，請按照以下格式輸出。

# Verification Report

## 1. 本次修改摘要

- 修改檔案：
- 主要修改：
- 對應新需求：

## 2. 新需求驗證

| ID | 新需求 | 結果 | 驗證依據 |
|---|---|---|---|
| N-01 | ... | PASS / FAIL / UNKNOWN | ... |

## 3. PRD 回歸驗證

| PRD 章節 / 條件 | 結果 | 驗證依據 |
|---|---|---|
| ... | PASS / FAIL / UNKNOWN / N/A | ... |

## 4. 測試與檢查結果

請列出實際執行的：

- Test
- Build
- Lint
- Type Check
- 其他驗證

以及各自結果。

## 5. 發現的問題

依嚴重程度分類：

### Critical
會破壞核心功能、資料或安全性的問題。

### High
會造成重要功能或 PRD 驗收失敗。

### Medium
有明顯問題，但不影響主要流程。

### Low
較小的問題或改善事項。

每個問題請提供：

- 問題描述
- 影響範圍
- 相關檔案
- 相關 PRD 條件
- 是否由本次修改造成
- 建議處理方向

目前只做 Review，**不要直接修改**。

## 6. 無法確認的項目

列出所有因環境、資料、權限或缺少測試而無法驗證的項目。

不要把這些項目當成 PASS。

## 7. 最終結論

最後只能根據實際證據做出以下其中一種結論：

### PASS
本次修改符合新需求，且沒有發現違反 `docs/PRD.md` 原有功能與驗收條件的回歸。

### PASS WITH RISKS
主要需求與 PRD 驗證通過，但仍有無法完整驗證的風險或項目。

### FAIL
本次修改存在未符合新需求，或已破壞 `docs/PRD.md` 原有功能 / 驗收條件的情況。

請同時列出判定依據。

---

## 十、驗證原則

請遵守以下原則：

1. **證據優先，不要猜測。**
2. PRD 驗收條件必須逐條對照。
3. 「Build 成功」不代表功能正確。
4. 「測試通過」不代表所有 PRD 條件都已驗證。
5. 沒有測試覆蓋的項目，要另外進行程式碼與流程檢查。
6. 無法確認的項目標示 `UNKNOWN`，不要強行判定 PASS。
7. 必須區分「本次修改造成」與「原本就存在」的問題。
8. 只進行 Review / Verification，不要擅自修改程式。
9. 所有重要結論都應指出相關檔案、測試或 PRD 章節作為依據。
10. **只有在有足夠證據時，才能宣告「沒有破壞既有功能」。**
