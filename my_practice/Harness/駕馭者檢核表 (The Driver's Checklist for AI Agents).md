## 設計哲學與適用情境

將生成式 AI 從「被動問答」轉化為「自主代理人（Autonomous Agent）」時，人類工程師的角色已從 **編碼者（Coder）** 轉變為 **駕馭者兼系統架構師（Driver & System Architect）**。

在給予 Agent 終端命令執行權、檔案修改權與網路請求權之前，必須先建立可控的防護邊界。本檢核表適用於：
- 使用自主 Coding Agent（如 Claude Code、Cursor Agent、Windsurf、Copilot Workspace 等）進行中大型專案開發。
- 團隊自建基於 LangGraph、AutoGen 或 CrewAI 的自動化 Agent 流程。
- 需要控制 API 預算、避免程式碼庫遭到非預期破壞的生產環境。

## 六大檢核維度與深度剖析

### 一、角色架構與職能分配
> **檢核問題**：誰負責規劃、執行、研究與最後整合？真的需要拆成多個角色嗎？

#### 深度解析
* **多 Agent 的協調稅（Coordination Tax）**：
  許多開發者傾向一開始就建立 Planner、Researcher、Coder、Reviewer 等多個角色。然而角色越多，上下文中傳遞的雜訊越多，容易出現角色互推責任或在確認禮儀上消耗大量 Token。
* **決策原則**：
  * **單一 Agent 貫穿**：若任務路徑單純、跨度短（例如修復特定 Bug、新增單一 API 端點），維持單一 Agent 完成「分析 ➔ 實作 ➔ 驗證」效果最佳。
  * **拆分獨立角色**：僅在「發散思考」與「收斂落地」產生衝突，或需要獨立視角審查時才拆分。
    * **Planner**：只負責需求分析、依賴性梳理與步驟規劃，不寫具體代碼。
    * **Executor**：專注局部模組的代碼實作與修改。
    * **Validator/Critic**：獨立負責執行測試、安全掃描與審查，不受 Executor 的主觀推論影響。

### 二、上下文治理與外顯記憶
> **檢核問題**：Agent 會讀取哪些專案資料？穩定規則是否已留在 AGENTS.md 或相關檔案？

#### 深度解析
* **短期工作記憶 vs. 外部長期記憶**：
  Prompt 是短暫且昂貴的。若依靠每次對話手動叮嚀架構規範，一旦對話歷史拉長，Agent 就會發生「注意力衰減（Attention Sinks）」，遺忘先前的承諾。
* **外顯化落地要求**：
  * **最小權限讀取**：嚴格限制檢索範圍，排除建置產物（`dist/`、`build/`）、大型二進位檔或全域測試 Log，避免 Context 爆量。
  * **專案憲章外顯化**：將不會輕易變動的架構鐵則、程式碼風格、語系要求與禁止事項固定於專案根目錄的 `AGENTS.md`（或 `.cursorrules` / `CLAUDE.md`）中，讓 Agent 在每次重置上下文時自動載入。

### 三、工具權限邊界 (Human-in-the-Loop)
> **檢核問題**：需要哪些工具？哪些操作可以自動執行，哪些必須先問人？

#### 深度解析
Agent 的生產力來自 Function Calling 與 Bash 終端權限，但這也是系統脆弱點。必須按操作的**可逆性**與**副作用**嚴格分級：

| 權限層級 | 操作屬性 | 典型情境 | 策略 |
| :--- | :--- | :--- | :--- |
| **Tier 1: 完全自動** | 唯讀 / 本機無害 | 讀取檔案、目錄樹列出、單元測試、Linter、靜態分析 | 允許自主執行，無需人類確認 |
| **Tier 2: 本機暫存** | 局部修改 / 可回復 | 修改受測檔案、建立本地測試檔、重構私有函式 | 允許自動執行，但需在乾淨 Git 分支 |
| **Tier 3: 強制確認** | 不可逆 / 高副作用 | 安裝第三方相依套件、資料庫 Migration、檔案刪除 (`rm`)、Git Push、呼叫外部扣款 API | **必須中斷執行，向人類申請授權後方可繼續** |

### 四、模型路由、合規與成本管理
> **檢核問題**：任務適合哪個模型與 Provider？資料能否送往該服務，預算上限是多少？

#### 深度解析
* **任務分級匹配（Model Routing）**：
  * **高階推理旗艦模型**：專門處理架構設計、核心難題排查、安全審查。
  * **快速高性價比模型**：專門處理重複性的單元測試編寫、靜態型別補齊、批次文字轉換。
* **資料隱私與法規合規**：
  * 包含個人身分識別資訊（PII）、客戶密鑰、專利核心算法之程式碼，是否符合傳輸至外部公有雲 API 的法規要求？
  * 必要時應採用地端私有化模型或具備零資料保留（Zero Data Retention, ZDR）政策的企業專屬通道。
* **財務與資源熔斷**：
  * 為每次任務設定最大 Token 消耗上限或單次預算警報，防範遞迴死循環。

### 五、完成定義 (DoD) 與回復機制
> **檢核問題**：什麼證據才算完成？測試失敗或結果不符時，回復點在哪裡？

#### 深度解析
* **摒除主觀回報，以客觀證據為準**：
  Agent 常出現「過度樂觀」的幻覺，聲稱「代碼已修復，功能運行正常」。駕馭者必須強制規定：**沒有執行測試輸出，就不算完成**。
  * 單元測試/整合測試全數通過（Green）。
  * 靜態檢查（Type Check / Lint）無新增警告。
  * `git diff` 僅包含必要變更，無殘留的 Debug 程式碼。
* **乾淨的快照回復點（Snapshot Checkpoint）**：
  * Agent 開始動工前，工作區必須保證為乾淨的 Git 狀態（Clean Tree），建議開立獨立分支（如 `agent/fix-xxx`）。
  * 一旦 Agent 產生結構性誤判，人類應能隨時透過 `git reset --hard` 或清除 Worktree 瞬間還原，無後顧之憂。

### 六、重試熔斷與中斷重構
> **檢核問題**：連續失敗幾次後是否要停下來重整問題，而不是繼續重投 Prompt？

#### 深度解析
* **死循環陷阱（Doom Loop）**：
  當 Agent 連續兩次修補同一個錯誤都失敗時，通常代表其**底層認知模型與現實架構不符**，或者**遺漏了隱藏的環境變數/相依限制**。此時繼續原句催促只會導致無效嘗試與 Token 浪費。
* **熔斷標準作業流程（SOP）**：
  1. **設定硬性上限**：同一錯誤連續修正失敗達 **2 次**，強制中斷 Agent 的自主權限。
  2. **要求結構化復盤**：要求 Agent 總結「嘗試了什麼」、「為何無效」、「推測的根本原因」。
  3. **問題重構（Reframing）**：由人類駕馭者介入，補充缺失的上下文、拆細問題層級，或提供關鍵斷點日誌後，重新發起任務。

## 快速檢核清單 (Cheat Sheet)

在敲下 Enter 把任務完全委派給 Agent 前，快速打勾確認：

- [ ] **角色清楚**：任務範圍單純嗎？是否避免了過度複雜的多 Agent 架構？
- [ ] **記憶備妥**：架構規範、程式風格已寫在 `AGENTS.md`，無須在對話中重複叮嚀？
- [ ] **排除雜訊**：讀取路徑是否已排除 `node_modules`、`dist`、Log 與二進位大檔？
- [ ] **權限防護**：破壞性指令（刪檔、資料庫修改、Git Push）已設定為必須人工確認？
- [ ] **模型合適**：當前模型等級符合任務複雜度？機敏資料已過濾或使用合規通道？
- [ ] **底線安全**：目前代碼處於乾淨的 Git 分支，能隨時一鍵 Rollback？
- [ ] **證據驗收**：已明確要求 Agent 提供自動化測試或終端指令綠燈輸出作為交付依據？
- [ ] **熔斷預備**：已約定連續失敗 2 次即刻暫停，嚴禁盲目反覆重試？

## 常見反模式 (Anti-Patterns)

1. **「保母式編程」**：人類逐行盯著 Agent 產出的每句程式碼，失去委託效益。應改為「定義驗收測試（DoD）與邊界，由機器自動驗收」。
2. **「許願式 Prompt」**：給予模糊目標如「把這個專案重構成現代化架構」，未提供範圍與限制，導致專案全面受損。
3. **「口頭完工信賴」**：看到 Agent 輸出「我已經修復了該 Bug」，未要求執行測試輸出便直接合併。
4. **「重試賭徒謬誤」**：報錯後不斷按「重試」或原樣發送「修好它」，期待模型下一次會靈光乍現，忽視架構資訊不足的事實。

## 落地配套：AGENTS.md 實施指引

將本檢核表落地的最高效方式，是在每個專案根目錄維護一份 `AGENTS.md`。

```
project-root/
├── AGENTS.md          <-- 放置於專案根目錄，寫明工具權限、DoD 與熔斷標準
├── src/
├── tests/
└── package.json
```

當 Agent 連線進入專案時，首要指令即是強制其讀取該規範，從而將被動的人工監督轉變為系統化的自動治理。
